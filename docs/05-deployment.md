# Deployment Architecture

> **Status (consolidated 2026-09-25):** the system runs on **one Supabase project**, `lgoirbfyspuflqekrcgp` (eu-west-1), served at `https://bibiani-restaurant.vercel.app`. It holds the real Bibiani Restaurant and the separate demo restaurant (isolated by RLS). The earlier DEV (`nkijnjovztglmwxoemqg`) and staging (`impairlsvhkumjzhjhti`) projects are **retired**: nothing depends on them, and the owner may pause or delete them. **Do not create new Supabase projects.** Automated tests run on in-memory PGlite and need no project. See [PRODUCT-CONSOLIDATION-REPORT.md](PRODUCT-CONSOLIDATION-REPORT.md).

## 1. The shape (modular monolith, no microservices)

```
                        ┌──────────────────────────── Cloud, one region (same as Supabase) ─────────────────────────┐
  Restaurant LAN        │                                                                                            │
 ┌──────────────────┐   │  app.<domain>  ── static web app (POS, KDS, display, admin) ── CDN (Vercel)                │
 │ POS / KDS /      │───┼─► HTTPS                                                                                    │
 │ customer display │   │  api.<domain>  ── API (Hono, Node 22+, stateless, ≥2 instances) ──┐                       │
 │ (browsers)       │◄──┼── WSS (Supabase Realtime: private "something changed" signals)     │ SQL as rp_api (RLS)   │
 │                  │   │                                                                     ▼                       │
 │ Print agent      │───┼─► HTTPS (device login)            Supabase: Postgres · Auth · Realtime · Supavisor pooler │
 │  └─TCP 9100─► printers (LAN only)                                                                                │
 └──────────────────┘   └────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **Browsers** talk to two services only: the API (all data) and Supabase Auth and Realtime (sign-in, change signals). They hold only public values: the Supabase URL, the anon key and the API URL.
- **The API** is the only component with database credentials. It connects as the least-privilege `rp_api` login. That login can only `SET ROLE app_api` (RLS applies) and call three identity functions.
- **The print agent** is the only process on the restaurant LAN that needs to reach printers. It needs **outbound HTTPS only**; nothing inbound is opened at the restaurant.
- The layers stay as in Clean Architecture. Hosting choices live in `apps/*` composition roots. Moving the API from Vercel to a container host changes no domain or application code.

## 2. Components and hosting

| Component | Host (recommended) | Why | Notes |
|---|---|---|---|
| Web app (`apps/web`) | Vercel static hosting / CDN | Static build, instant rollback, managed TLS | `VITE_*` public env only; `/v1` routed to the API on the same site, or `VITE_API_URL` + API `ALLOWED_ORIGINS` |
| API (`apps/api`) | Vercel Functions (Node runtime, Fluid compute) **in the Supabase region** (eu-west-1 for DEV) | No servers to run, instant rollback | Must be co-located: each order submission is ~44 database statements (§7) |
| API, alternative | Small container host (Fly.io / Railway / Render), 2 instances | Long-lived pooled connections, no cold starts | Same code, same env vars |
| Database, Auth, Realtime | Supabase (DEV / STAGING / PROD projects) | Required platform | PROD on a paid plan with PITR (§6) |
| Scheduled jobs | Supabase `pg_cron` | Device offline sweep every minute (migration 1100) | Verified scheduled on DEV |
| Print agent (`apps/print-agent`) | Always-on machine on the restaurant LAN (mini PC / Raspberry Pi / the back-office PC) as a system service | Must reach printers over TCP 9100 | systemd unit or Windows service; auto-restart; journal on local disk |

## 4. Configuration and secrets

| Variable | Where | Secret? |
|---|---|---|
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | API, print agent, web (`VITE_` copies) | public |
| `DATABASE_URL` (`rp_api` login) | API only | **secret** |
| `SUPABASE_SECRET_KEY` (`sb_secret_…`) | API only: creates staff and device logins through the Auth admin API | **secret** |
| `ALLOWED_ORIGINS`, `DEVICE_ACCOUNT_DOMAIN`, `DB_*_TIMEOUT_MS`, `PORT` | API | no |
| `API_URL`, `AGENT_REFRESH_TOKEN` | print agent | refresh token is **secret** (agent machine only) |
| `TEST_DATABASE_URL`, `PLATFORM_DATABASE_URL` | developer machine / CI for DEV only | **secret**, never deployed |

- Secrets live in the host's secret store (Vercel project env vars, encrypted), never in git.
- `pnpm security:scan` fails CI if a Supabase secret key, a database URL with a password, a `service_role` JWT, or any exact secret value from the environment appears in any build output (web bundle, API, agent). It was self-tested against planted fakes.
- Rotating DEV logins: `pnpm dev:logins` generates new passwords and updates `.env`.

## 5. DNS and TLS ☐

- `app.<restaurant-domain>` → web host; `api.<restaurant-domain>` → API host. Both have managed TLS certificates (automatic on Vercel).
- Supabase endpoints use Supabase's TLS.
- The restaurant network needs outbound 443 only. Printers get fixed LAN IPs (DHCP reservations) so printer addresses stay valid.

## 6. Backups and disaster recovery ☐

- PROD must have **Point-in-Time Recovery** enabled (a paid add-on). Confirm it is active on the actual plan before go-live; don't assume daily backups are enough.
- Targets to agree with the owner: RPO ≤ 5 min, RTO ≤ 2 h.
- Nightly `pg_dump` of PROD to separate storage as an independent copy.
- A quarterly restore drill into STAGING, timed and recorded (backlog QA-03).

## 7. Performance facts that shape hosting (measured)

| Operation | DB statements (query budget test) | From a laptop ~140 ms from eu-west-1 | Expected co-located (~1–2 ms/statement) |
|---|---|---|---|
| Submit order (4 stations) | 44 | ~14 s first call, several seconds warm | ≈ 0.1–0.2 s |
| KDS ticket ready | 16 | ~5 s | < 0.1 s |
| Record payment | 13 | — | < 0.1 s |
| KDS board load | 5 | — | < 50 ms |
| Realtime delivery, commit → subscriber | — | 64 ms observed | same |

**Conclusion:** the API must run in the same region as the database. The co-located figures are estimates from the statement counts; they get measured on STAGING (☐).

## 9. CI/CD

- **CI (every PR / push to main)** — `.github/workflows/ci.yml`:
  1. lint and format
  2. typecheck
  3. migrations applied from an empty database, with RLS checked on every table
  4. unit and integration tests (120, PGlite)
  5. build
  6. secret scan
- **Hosted validation (manual or nightly, needs DEV secrets):**
  - `pnpm test:hosted`: the same suites against DEV, plus real concurrency and real realtime
  - `pnpm test:e2e`: browser scenarios
- **CD ☐:**
  1. Merge to `main`.
  2. `supabase db push` to STAGING.
  3. Deploy the API and web preview.
  4. Run smoke tests and the Playwright scenarios against STAGING.
  5. Get manual approval.
  6. `supabase db push` to PROD.
  7. Promote the deployments.

## 10. Rollback

- **API / web:** redeploy the previous build (instant on Vercel).
- **Database:** never down-migrate in production. Ship a forward-fix migration instead. Migrations must stay backward compatible with the previous API version (expand, then contract).
- **Print agent:** keep the previous build on the machine and switch the service back. Its journal format is backward compatible.
